### 1. OpenAI Predicted Outputs — the most direct competitor

**Source (PRIMARY):** https://developers.openai.com/api/docs/guides/predicted-outputs (fetched 2026-09-07; the old `platform.openai.com/docs/guides/predicted-outputs` 301-redirects here).
**Announced:** 2024-11-04. Confirmed by Simon Willison's note of that date, https://simonwillison.net/2024/Nov/4/predicted-outputs/ [PRIMARY for the date/quote].

**Mechanism.** You pass `prediction: {type: "content", content: "<what you expect the output to be>"}` on Chat Completions. OpenAI's Steve Coffey (quoted by Willison, 2024-11-04): *"We are using the prediction to do speculative decoding during inference, which allows us to validate large batches of the input in parallel, instead of sampling token-by-token!"* So it is **server-side speculative decoding with a user-supplied draft**. The draft is not a draft *model*; it is literally the old document.

**Supported models (as documented 2026-09-07):** GPT-4o, GPT-4o-mini, GPT-4.1, GPT-4.1-mini, GPT-4.1-nano. Note what is NOT on that list: the o-series / reasoning models, and (as far as the doc goes) GPT-5 family. Flag for follow-up.

**BILLING CAVEAT — verified, and it is the crux.** Doc text: *"Any rejected tokens are still billed like other completion tokens generated by the API, so Predicted Outputs can introduce higher costs for your requests."* The usage object returns `completion_tokens_details.accepted_prediction_tokens` and `.rejected_prediction_tokens`. Rejected prediction tokens are charged at **completion (output) token rates**. OpenAI's stated reason: when the model diverges from the speculation, they do additional sampling to discover the net-new tokens.

=> **Predicted Outputs buys LATENCY, never money.** Best case (100% accepted) you pay exactly what full regeneration costs. Worst case you pay MORE than full regeneration. There is no discount branch. This is the single most important fact for our cost model.

**Unsupported parameters when `prediction` is set (from the doc's limitations list):**
- `n` > 1
- `logprobs`
- `presence_penalty` > 0
- `frequency_penalty` > 0
- `audio` options
- **`tools` — function calling is NOT supported**
- `modalities` other than text
- `max_completion_tokens`

The `tools` exclusion is a serious hit for our problem area and needs following up: if `response_format`/Structured Outputs is likewise excluded, Predicted Outputs cannot be applied to schema-constrained JSON at all, which would kill it as a competitor to this project. CHECKING NEXT.

### 2. Prompt lookup decoding / n-gram speculation — the open-source version of the same idea

**Source (PRIMARY):** https://github.com/apoorvumang/prompt-lookup-decoding (Apoorv Saxena). Fetched 2026-09-07.

Mechanism: replace the draft *model* in speculative decoding with plain **string matching**. Take the last few generated tokens, search the prompt for that n-gram, and if found, propose the tokens that followed it as the draft. Zero extra model, zero extra memory, no training. It exploits "high n-gram overlap between LLM input and output" in input-grounded tasks.

Reported numbers (README, Mistral-7B-Instruct on A100, greedy decoding): **~2.4x average on summarization and context-QA**; small gains on multi-turn chat turn 0; similar-to-summarization gains at turn 1; "very high gain" on coding turn 2 where the model copies code out of context. Defaults: max n-gram size 3, continuation length 10, and the author himself says these were "chosen on very little testing." README claims speedup with "no effect on output quality" but publishes no quality metrics.

Upstreamed:
- **HuggingFace `transformers`**: `model.generate(..., prompt_lookup_num_tokens=10)` [PRIMARY, from the README].
- **vLLM**: `speculative_model="[ngram]"` in the older API; current API below.

**vLLM (PRIMARY):** https://docs.vllm.ai/en/latest/features/speculative_decoding/ (fetched 2026-09-07; the older `/features/spec_decode.html` redirects here). Supported proposers as of that page: EAGLE, MTP, draft models, PARD, **n-gram / prompt-lookup**, suffix decoding with dynamic depth, MLP speculator, custom proposer backends, dynamic speculative decoding, adaptive verification. N-gram config: `{"method": "ngram", "prompt_lookup_min": N, "prompt_lookup_max": M, "num_speculative_tokens": K}` — defaults `prompt_lookup_min`/`max` = 5.

**LOSSLESSNESS — this is the decisive correctness fact for the pro-regeneration case.** vLLM doc, verbatim: *"Speculative decoding sampling is theoretically lossless up to the precision limits of hardware numerics."* vLLM ships tests asserting *"greedy sampling with speculative decoding matches greedy sampling without it."* So speculative decoding does not change what the model says — it only changes how fast it says it. This is the standard Leviathan/Chen rejection-sampling guarantee (verify below).

**llama.cpp (PRIMARY):** https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md. Supports draft models, EAGLE-3, DFlash, DSpark, MTP heads, and five n-gram variants: `ngram-simple`, `ngram-map-k`, `ngram-map-k4v`, `ngram-mod`, `ngram-cache`. Doc explicitly names "rewriting of source code" and "iterating over a block of text/code" as the target workloads — i.e. exactly our problem. Its own example acceptance rates: 0.576 (171/297) and 0.703 (90/128). It notes exact output matching across backends requires greedy sampling because of floating-point differences.

**A hard NEGATIVE result for the speculative case, worth weighting heavily.** https://github.com/thc1006/qwen3.6-speculative-decoding-rtx3090 — a public benchmark of llama.cpp speculative decoding on Qwen3.6-35B-A3B on a single RTX 3090 (post PR #19493, dated 2026-04-19), 19 configurations across `ngram-cache`, `ngram-mod`, and a classic vocab-matched draft (Qwen3.5-0.8B). Stated finding: **"no variant achieves net speedup on Ampere + A3B MoE."** [SECONDHAND — from the repo description in search results; I have not read the raw JSON.] The lesson generalises: speculation gains are hardware- and architecture-dependent and can be zero or negative. vLLM's own doc hedges the same way: gains depend on "model family, traffic pattern, hardware, and sampling settings," and n-gram methods give only "modest speedups" under peak traffic — because speculation trades *extra compute* for *fewer sequential steps*, and under high batch utilisation there is no spare compute to trade.

#### THE SHARP DISTINCTION, stated plainly

**Every speculative technique in sections 1–3 reduces wall-clock time. Not one of them reduces the billed output-token count.** Predicted Outputs is worse than neutral: it can *raise* the bill via `rejected_prediction_tokens` charged at the output rate. Open-source speculative decoding (vLLM, llama.cpp) reduces your GPU-seconds if you own the GPU, so on self-hosted infrastructure the latency win *is* a cost win — but on any per-token API it is not.

So: **the user's argument for deltas splits cleanly into two halves, and the existing machinery only kills one of them.**
- The *latency* argument against full regeneration: substantially answered by speculative decoding + Predicted Outputs, in the edit case. Concede it.
- The *money* argument: untouched. An output token costs **50x** a cached input token on GPT-5.6 Sol, Opus 5, Sonnet 5 and Haiku 4.5, **60–80x** on GPT-5.5/GPT-5/Terra/Luna, and **200x** on Claude Fable 5.1. Regenerating N tokens of unchanged content costs N output tokens no matter how fast you do it. This is the strongest single fact in favour of the whole project and I could not find anything that refutes it.
- The *ceiling* argument (max output tokens, quality decay over long generations): also untouched. Speculative decoding does not raise `max_tokens`. Notably, `max_completion_tokens` is on the *unsupported* list for Predicted Outputs, so if anything the ceiling problem gets slightly worse there.

### 3. Speculative decoding generally — and the hard ceiling on how much it can help

**Leviathan, Kalman, Matias, "Fast Inference from Transformers via Speculative Decoding", ICML 2023 oral, arXiv:2211.17192** [PRIMARY, formulas read from https://ar5iv.labs.arxiv.org/html/2211.17192].
- Reported: **2x–3x** acceleration on T5-XXL vs the standard T5X implementation, "with identical outputs", no retraining and no architecture change.
- Expected tokens per iteration (Eq. 1): **E(# generated tokens) = (1 − α^(γ+1)) / (1 − α)**, with α the acceptance rate and γ the number of speculative guesses per step.
- Expected walltime improvement factor (Theorem 3.8): **(1 − α^(γ+1)) / ((1 − α)(γc + 1))**, where c is the cost of one draft-model run relative to one target-model run.
- Distribution guarantee, verbatim: speculative sampling *"guarantee[s] an identical output distribution for any choice of approximation model"*, giving outputs with "the same distribution as those from the target model alone."

**Chen, Borgeaud, Irving, Lespiau, Sifre, Jumper, "Accelerating Large Language Model Decoding with Speculative Sampling", arXiv:2302.01318** — the contemporaneous DeepMind paper; same modified-rejection-sampling scheme, demonstrated on Chinchilla 70B. [Cited from memory of the literature and consistently reported across the surveys below; I did NOT fetch it directly this session — mark SECONDHAND until someone opens it.]

**THE CEILING — this is the number that decides the argument.** Plug the copy case into Theorem 3.8. For prompt-lookup decoding the "draft model" is a string search, so **c ≈ 0**, and the formula collapses to the expected-tokens formula. As **α → 1** (a perfect draft, which is exactly the "regenerate a document with one small change" case), (1 − α^(γ+1))/(1 − α) → **γ + 1**.

So: **the maximum possible speedup from any speculative method is γ+1 — one more than the number of tokens you speculate per verification pass.** It is not unbounded. And γ is bounded in practice, because verifying γ+1 positions in one forward pass is free only while decoding is memory-bandwidth-bound (small batch); once the batch is large enough to be compute-bound, the extra positions cost real FLOPs and the gain shrinks. That is precisely why vLLM's doc warns that n-gram methods deliver only "modest speedups" under peak traffic, and why the RTX 3090 / Qwen3.6 MoE benchmark found *no* net speedup — an A3B MoE at batch 1 on Ampere is not in the regime where free parallel verification exists.

Real-world γ values are small: prompt-lookup's default continuation is **10 tokens** (ceiling ≈ 11x); vLLM's n-gram defaults are `prompt_lookup_min/max = 5`. So the honest ceiling for the copy case is roughly **5x–20x latency**, with **zero** reduction in billed output tokens on any per-token API.

**Compare that with what fragment emission gives you.** If a document is N tokens and only k change, emitting k tokens instead of N is an **N/k** reduction in *both* latency and dollars. For the 10,000-row table emitted 10 rows at a time, or a 20,000-token form where 30 tokens change, N/k is 100x–1000x. Speculative decoding's ceiling of ~γ+1 is not in the same order of magnitude, and it is a latency-only win. **This is the single cleanest quantitative reason the two approaches are not substitutes.**

**Published speedups for the main methods** (all single-batch or low-batch, all latency-only):

| Method | Reported speedup | Source | Provenance |
|---|---|---|---|
| Speculative decoding (Leviathan) | 2x–3x on T5-XXL | arXiv:2211.17192 | PRIMARY |
| Prompt lookup decoding | ~2.4x on summarization/context-QA (Mistral-7B, A100, greedy); "very high" on code-copy turns | github.com/apoorvumang/prompt-lookup-decoding | PRIMARY |

Note that EAGLE-3's 6.5x is the high-water mark in the literature and it comes with τ ≈ 4–7.5, i.e. γ+1 ≈ 5–8. That is consistent with the ceiling analysis: the field's best result is roughly "one verification pass yields 5–8 tokens." Nothing published approaches 100x.

**Correctness.** Standard speculative decoding, speculative sampling, EAGLE, Medusa-1, REST and n-gram lookup all use the modified rejection-sampling verification and are **output-distribution-preserving**. vLLM asserts and tests this ("theoretically lossless up to the precision limits of hardware numerics"; "greedy sampling with speculative decoding matches greedy sampling without it"). Medusa-2 with typical acceptance is the notable exception — typical-acceptance relaxes exactness for throughput. **Concession to the pro-regeneration side: whatever correctness problems full regeneration has, speculative decoding does not add any. It is a pure latency transform.** But by exactly the same token — and this is the trap — **it cannot remove any correctness problem either.** If the model would have silently altered row 4,317 while regenerating, speculative decoding faithfully reproduces that alteration; the draft is rejected at that position and the model's own (wrong) token is sampled. See section 7.

### 7. Is the pain real? Evidence on the CORRECTNESS failure mode

This is where my adversarial brief runs into trouble, so I am reporting it in full.

**(a) "Where vs What: Decomposing Structural and Content Failures in LLM-Generated Structured Outputs"** — Yiwei Zhang, Chengke Wu, Li Wang, Jianqiang Li, arXiv:2608.25358v1, **2026-08-26**. [PRIMARY, fetched 2026-09-07 from https://arxiv.org/html/2608.25358]

The paper defines **Displacement Rate (DR) = 1 − VPA/VP**: the fraction of values that the model produced *correctly* but placed at the *wrong structural position* in the output. Measured on six models (GPT-4o, DeepSeek-V3, DeepSeek-V4-Flash, Qwen3-8B, Qwen2.5-14B, Qwen2.5-7B). At their highest complexity level:

| Model | Displacement rate |
|---|---|
| DeepSeek-V4-Flash | 35.4% |
| DeepSeek-V3 | 26.2% |
| GPT-4o | 24.2% |
| Qwen2.5-14B | 49.2% |
| Qwen2.5-7B | 73.8% |

And it scales with schema depth: for Qwen2.5-7B, DR rises "from near-zero to 28.5%" as recursive depth goes 1 → 3. Headline finding, verbatim: **"structural fidelity degrades earlier and faster than content accuracy"** as task complexity increases. The authors describe a "scissors pattern" — value presence stays high while value *placement* accuracy collapses.

Caveat on how much weight this carries: the task studied is extraction-into-a-schema, not regeneration-with-a-small-edit. It does not directly measure "the model corrupted a region it was only told to copy." What it *does* establish, from a primary source with numbers, is that **the probability of a structural error in a schema-constrained generation grows sharply with the size and depth of the object being emitted** — which is the mechanism the fragment-emission proposal is meant to defuse. A fragment generation is, by construction, a shallow low-complexity schema task; a 10,000-row emission is the deepest, most complex one you can construct. Constrained decoding guarantees the output *parses*; nothing guarantees it is *right*.

**(b) Aider's laziness benchmark — direct evidence of models eliding content they were told to reproduce.** [PRIMARY: https://aider.chat/docs/unified-diffs.html]

89 Python refactoring tasks from 9 open-source repos. With SEARCH/REPLACE (a whole-block rewrite format), **GPT-4 Turbo 1106-preview emitted lazy placeholder comments — `# ...add logic here...`, i.e. it deleted real code and replaced it with a promise — on 12 of 89 tasks (~13%)**. Switching to unified diffs cut that to **4 of 89 (~4.5%)**, the "3X less lazy" result. Aider's test explicitly checks that "the new top-level function must contain approximately the same number of AST nodes as the original class method" — i.e. they had to build an automated detector for silent content loss during a full rewrite, because it happened often enough to matter. GPT-4 (0613) went from 26% to 59% on the benchmark when moved to unified diffs.

This is code, which is out of scope as a *target*, but it is in scope as *evidence of the failure mode*: when a model is asked to reproduce a large artifact with a small change, it sometimes does not reproduce it. **And the fix that worked was making the model emit a delta instead of the whole artifact.** That is our proposal, validated in an adjacent domain, four years ago, by measurement.

**(c) Aider's own counter-evidence, reported for balance.** Aider's docs also note that the `whole` format "is the easiest for an LLM to use," and one benchmark write-up found the whole-file format "tends to be more stable overall" across single- and multi-turn tasks, because diff formats introduce their own failure mode — the model emits a patch that will not apply. Gemini 2.5 Flash (diff) was observed "frequently hit[ting] the maximum allowed reflections (three attempts) without successfully applying the code diff." [SECONDHAND, from search snippets of aider.chat/docs/more/edit-formats.html and arXiv:2510.13859.] **This is a real cost of the delta approach and the project should not pretend otherwise: full regeneration cannot fail-to-apply, and a delta can.** The schema-constrained version of the idea partly answers this — a fragment validated against its own sub-schema and spliced by *code* at a known path is much safer than a model-authored textual patch — but the failure mode of "the model chose the wrong path to edit" replaces it and does not disappear.

**(d) Structured-output quality under constraint, general.** [SECONDHAND, search snippets] Reported findings circulating in this literature: models produce nearly-perfect *syntax* while a sizeable fraction of leaf values are wrong, with a 15–25 point gap between schema validity and value correctness; and forcing JSON *during reasoning* costs 10–15% accuracy on math/symbolic tasks versus reasoning free-form then formatting. Related primary-looking sources I did not fetch: "The Structured Output Benchmark" arXiv:2604.25359, "SLOT: Structuring the Output of Large Language Models" arXiv:2505.04016, "The Hidden Cost of Structured Generation in LLMs: Draft-Conditioned Constrained Decoding" arXiv:2603.03305. **Flagged for another agent to verify — I am marking these unverified.**

### THE MOST IMPORTANT PAPER I FOUND — and it cuts against the proposal

**"JSON Whisperer: Efficient JSON Editing with LLMs"** — Sarel Duanis, Asnat Greenstein-Messica, Eliya Habba (Lightricks; Habba also Hebrew University). arXiv:2510.04717v1, **2025-10-06**. | Metric | Result |
|---|---|
| Token reduction vs full regeneration | **31%** |
| Edit quality vs full regeneration | **within 5%** (i.e. slightly *worse*, not better) |
| Latency improvement, Claude Sonnet | **42.3%** (≈1.73x) |
| Latency improvement, GPT-4o-mini | **31.5%** (≈1.46x) |
| Dataset | ~400 synthetic examples, film-production scenarios, generated with Claude Sonnet |
| Models evaluated | GPT-4o-mini and Claude Sonnet, zero-shot and few-shot, four complexity levels (simple, creative, complex, list manipulation) |

Two further findings that matter enormously for anyone designing this:
1. **Plain RFC 6902 does not work with LLMs.** The authors had to invent **EASE (Explicitly Addressed Sequence Encoding)**, which turns arrays into dictionaries with stable keys instead of numeric indices, because "LLMs struggle with array index arithmetic" and "frequently miscalculate these shifts or conflate zero-based and one-based indexing." The naive version of the delta idea — ask for a JSON Patch against the real document — **fails on array addressing**.
2. **Models "miss necessary updates" when editing via fragmented patches.** Changing one field often implies changing a related field, and a model looking at only a fragment does not see the implication. Full regeneration does not have this failure mode.

**What this does to the case for the project, stated bluntly:**
- 31% token savings and ~1.5–1.7x latency, at the cost of a custom encoding, a new class of addressing bugs, and a 5% quality regression, is a **worse deal than Predicted Outputs**, which claims 3–5x latency for zero schema engineering and zero quality change.
- It is the strongest single piece of evidence for my brief, and it is a primary, peer-reviewed, industry-track result.

**The one honest reason not to over-weight it:** their documents are film-production JSON objects from a ~400-example synthetic set — small. A patch has fixed overhead per operation (`op`, `path`, `value` scaffolding), so at small N the patch is nearly as long as the document and 31% is what you get. The N/k advantage only becomes large when N is large. **The paper does not test the regimes the user actually cares about** — a 20,000-token form, or a 10,000-row table. Anyone citing 31% as the ceiling is extrapolating from the small-N regime. Anyone citing N/k as the expected saving is extrapolating from arithmetic that this paper's measured overheads partially contradict. **The correct conclusion is that nobody has measured the large-N regime, and that is a gap worth filling.**

### An interaction that damages BOTH sides: constrained decoding has its own overhead

## 7b. THE DECISIVE CORRECTNESS EVIDENCE — and it goes against my brief

I was asked to find evidence, for or against, that models silently alter regions they were only meant to copy while regenerating a large structured object. **I found it, from two independent primary sources, and it is strong. This is the one failure mode speculative decoding cannot fix, and it is measured.**

### (A) "LLMs Corrupt Your Documents When You Delegate" — DELEGATE-52

**Philippe Laban, Tobias Schnabel, Jennifer Neville. arXiv:2604.15597, submitted 2026-04-17.** [PRIMARY — abstract fetched 2026-09-07 from https://arxiv.org/abs/2604.15597]

- Benchmark simulates extended delegated workflows requiring document modifications across **52 professional domains**, including coding, crystallography and music notation.
- **19 LLMs evaluated**, including the frontier tier: Gemini 3.1 Pro, Claude Opus 4.6, GPT-5.4.
- Headline result, from the abstract: frontier models **"corrupt an average of 25% of document content by the end of long workflows."** Non-frontier models are worse.
- Degradation severity **increases with document size, interaction length, and the presence of distractor files.**
- Methodology uses domain-specific parsers and reversible edits ("round-trip relay") to measure semantic fidelity without gold references. [Methodology detail is SECONDHAND, from a search snippet — the abstract fetch did not carry it.]
- Reported mitigations include limiting interaction length, chunking context, better filtering of distractors, and **"full rewrites (preferring patches instead)"** — [SECONDHAND, from a search snippet; I could not confirm this line from the abstract. Someone should open the full text and confirm, because if the paper explicitly recommends patches over full rewrites, that is an independent endorsement of the project's thesis by a Microsoft Research group.]

This is the failure mode the user hypothesised — "retyping untouched regions lets the model silently corrupt them" — named, benchmarked, and quantified at 25% content corruption on frontier models. It is not hypothetical.

### (B) "Verbatim Data Transcription Failures in LLM Code Generation: A State-Tracking Stress Test"

**Mohd Ariful Haque, Kishor Datta Gupta, Mohammad Ashiqur Rahman, Roy George. arXiv:2601.03640v1, 2026-01-07.** [PRIMARY, fetched 2026-09-07 from https://arxiv.org/html/2601.03640v1]

The cleanest possible isolation of "can a model copy N items without altering them?" Models are given a list of high-precision decimal constants and must emit Python code containing those values **verbatim** while doing trivial arithmetic. Validation is exact substring matching.

| Number of items N | Perfect runs | Mean match rate |
|---|---|---|
| 100 | 44–45% | — |
| 300 | **0%** | **15.65%** |
| 500 | **0%** | **7.12%** |

Verbatim from the paper: *"Long outputs reveal two problems at once: a capacity-limited ceiling that prevents complete transcription, and state-tracking derailments."* And on the danger: *"a generated file that looks like correct code can embed a subtly corrupted dataset"* while executing without errors.

**Important caveat, and I want it recorded honestly: the 11 models tested are all open-weights** — GPT-OSS 20B/120B, Llama 3.3 70B, DeepSeek Coder 236B, DeepSeek R1 70B, Mistral 123B, Qwen3-Coder 30B, Codestral 22B, CodeGemma 7B, CodeLlama 34B. **No frontier closed model (GPT-5.x, Claude Opus 5, Gemini 3.x) was tested.** The absolute numbers therefore do not transfer to a GPT-5.6 or Opus 5 workload. But the *shape* — a cliff between N=100 and N=300, and zero perfect runs beyond it — is exactly the shape DELEGATE-52 finds on frontier models at 25% corruption, so the two results corroborate each other across model tiers.

### What this does to my brief

**It is fatal to the correctness half of it.** My assignment was to argue that existing machinery removes the pain. Speculative decoding is *provably* distribution-preserving (Leviathan Thm; vLLM's lossless test). That is exactly why it is useless here: **it faithfully reproduces the corruption.** If a model would have dropped 25% of the document while regenerating it, Predicted Outputs makes it drop 25% of the document 3–5x faster and bills you for the rejected tokens on the way. There is no version of speculative decoding that fixes a wrong token, because a wrong token *is* the model's true output distribution and the algorithm's entire guarantee is that it will not change it.

**NEGATIVE RESULT worth stating precisely:** I found no published measurement of copy-fidelity for a *schema-constrained JSON* regeneration specifically — everything above is prose documents (DELEGATE-52) or code (verbatim transcription, Aider). Queries tried: `LLM rewriting long document silently changed unchanged sections copy fidelity failure measurement`; `LLM structured output long JSON generation quality degradation many rows accuracy drops output length`; `"structured output" LLM production cost regenerating entire object every turn engineering blog bottleneck`. The closest schema-specific evidence is the Displacement Rate work (arXiv:2608.25358, §7a), which measures misplacement in extraction rather than in copy-preserving regeneration. **The exact experiment — regenerate a large Pydantic-schema object with one field changed, and diff the other fields — appears not to have been run. That is a cheap experiment and a publishable gap.**

#### 7b(A) follow-up — DELEGATE-52 detail

[SECONDHAND, via https://www.emergentmind.com/papers/2604.15597 — note that emergentmind is a paper-summary site with AI-generated commentary, so treat its wording as a pointer, not as the authors' words. Someone should read the actual PDF.]

- **Round-trip relay methodology:** chains *reversible* edits — a forward transformation (e.g. split a ledger) followed by its inverse (merge it back) — and measures reconstruction after each cycle by comparing the original to the reconstructed version. This measures semantic loss with **no gold reference needed**, which is a genuinely clever design and is directly reusable for testing a structured-write system.
- **Document size effect:** *"Each 1k-token increment progressively increases degradation, with the effect amplifying over multiple iterations."* — i.e. corruption is a function of N, the document size. Exactly the scaling the fragment proposal is designed to break.
- **Horizon effect:** *"Degradation accelerates with horizon length; no plateau is observed up to 100 interactions."* No self-correction, no saturation.
- **Across all models, mean reconstruction score after 20 interactions falls to ~50%** — half the semantic content lost or corrupted. Frontier models: 25%.
- The summary site lists as a practical application: *"Require LLMs to output structured minimal diffs (e.g., unified diff, JSON patch, AST edit scripts) and apply them programmatically."* **Flagged as possibly AI-generated commentary rather than the paper's own recommendation — verify before citing.**

## 6. THE HONEST COST MODEL

All prices dated **2026-09-07**, sources in section 4+5 above. This section is arithmetic on those prices plus stated engineering assumptions; the assumptions are where it can be wrong, so they are listed first and each is flagged.

### Assumptions (challenge these before challenging the conclusions)

| Symbol | Meaning | Value used | Basis |
|---|---|---|---|
| N | tokens in the full structured object | varies | — |
| k | tokens whose *value* changes | varies | — |
| k' | tokens actually emitted by fragment emission | k + overhead | overhead = the schema path/wrapper plus the rest of the smallest schema node containing the change. From JSON Whisperer, at small N this overhead is large enough to cap savings at 31%. |
| r | output token rate | **80 tok/s** | ASSUMPTION. Nominal frontier standard-speed rate, 2026. Anthropic fast mode is "up to 2.5x higher output tokens per second" than standard on Opus 5, which brackets the range. |
| TTFT | time to first token | **0.8 s** | ASSUMPTION, order-of-magnitude only. |
| S | speculative speedup factor | **3x central**, 5x optimistic, 1x pessimistic | OpenAI claims "3-5x for rewrite and code editing"; published methods cluster 2-3x; EAGLE-3 tops out at 6.5x; the Qwen3.6 / RTX-3090 benchmark found 1.0x. |
| R | rejected prediction tokens | O(k), small when k is small | Speculation only misses near change sites; the speculator overshoots by at most gamma per site. |
| p_in / p_cache / p_out | per-MTok prices | GPT-5.6 Sol $4 / $0.40 / $20; Claude Opus 5 $5 / $0.50 / $25 | section 4+5, PRIMARY |

**Inference, not a documented fact:** the `prediction` content does **not** appear to be billed as input tokens. In Azure's own FizzBuzz example the same ~75-token code block is sent twice (once in `messages`, once in `prediction`) and `prompt_tokens` is 124 — consistent with the code counted **once** plus ~25 tokens of instructions and ~15 of chat scaffolding, not with it counted twice (~200). **This is my arithmetic on their example, not a statement in any doc. Verify before relying on it.**

**The old document is sent as input in all three approaches.** The model has to see it. So input cost is a *common term* and cancels out of the comparison — except that it sets a **floor** below which no approach can go.

### The floor: what resending the document as input costs

| Provider / mode | Cost of resending N tokens as input, as a percentage of what full regeneration of N tokens costs |
|---|---|
| GPT-5.6 Sol, cached input ($0.40 vs $20 out) | **1.96%** |
| Claude Opus 5, cache read ($0.50 vs $25 out) | **1.96%** |
| Claude Fable 5.1, cache read ($0.25 vs $50 out) | **0.50%** |
| Claude Opus 5, **uncached** input ($5 vs $25 out) | **16.7%** |
| Claude Opus 5, **first turn** (cache write $6.25) | **20.0%** |
| Gemini, cached (10% of input, ~5:1 out:in) plus $0.50/MTok/hour storage | ~2% plus rent |

**The "input is cheap and cacheable, output is not" premise VERIFIES.** Once warm, resending the whole document costs ~2% of regenerating it — and 0.5% on Claude Fable 5.1. It does not verify on a cold cache (17-20%), and Google additionally charges rent for cache residency. But for any workload with repeated turns inside the TTL, the premise holds with room to spare.

### Worked example 1 — the form edit (the user's motivating case 1)

N = 20,000 tokens (a large Pydantic form object). One answer changes: k is about 30. The smallest schema node containing it is a question sub-object: **k' = 120**. Claude Opus 5, warm cache.

| | Billed input | Billed output | **Dollars** | **Wall clock** | Error exposure |
|---|---|---|---|---|---|
| (i) Full regeneration | 20,000 at $0.50/M = $0.0100 | 20,000 at $25/M = $0.5000 | **$0.5100** | 0.8 + 20000/80 = **250.8 s** | Model re-decides 19,880 tokens it was told to copy |
| (ii) Full regen + Predicted Outputs (S=3, R=200) | $0.0100 | 20,200 at $25/M = $0.5050 | **$0.5150** (more than (i)) | 0.8 + 20000/240 = **84.1 s** | **Identical to (i), provably** |
| (iii) Fragment emission | $0.0100 | 120 at $25/M = $0.0030 | **$0.0130** | 0.8 + 120/80 = **2.3 s** | 120 tokens re-decided; plus routing and missed-related-update risk |

**(iii) vs (i): 39x cheaper, 109x faster. (iii) vs (ii): 40x cheaper, 37x faster.**

Note also that (ii) is *more expensive than doing nothing clever at all*, and that it does not exist on the Anthropic API — this row is hypothetical for Claude and real only on OpenAI / Cerebras / Fireworks / Mistral.

Sanity check on the latency figure that makes this case: a 20,000-token structured output at a nominal 80 tok/s is **over four minutes**. That is not a micro-optimisation; it is the difference between an interactive form and a batch job. Speculation at 3x brings it to 84 s — still not interactive. Only fragment emission gets to 2.3 s.

### Worked example 2 — the 10,000-row table (the user's motivating case 2)

10,000 rows times 40 tokens = **400,000 output tokens**.

**Full regeneration is not expensive here. It is impossible.** Max output tokens per response, as of 2026-09-07: Claude Opus 5 / Opus 4.8 / Fable 5 / Fable 5.1 / Sonnet 5 / Sonnet 4.6 = **128,000** [PRIMARY-ish, from the bundled `claude-api` skill]; Haiku 4.5 = 64,000; GPT-5.4 = 128K and Gemini 3.1 Pro = 65,536 [both SECONDHAND, from search]. 400,000 exceeds all of them by 3-6x. **No decoding technique raises this ceiling.** Speculative decoding makes you hit the wall faster.

So the only question is how you chunk, and the interesting cost is on the **input** side:

| Chunking strategy | Total billed input | Output | Dollars (Opus 5, cached input) | Wall clock |
|---|---|---|---|---|
| One 400k-token call | — | — | **N/A — exceeds max_tokens** | — |
| 1,000 calls of 10 rows, **each call re-sees all prior rows** | about 2.05e8 tokens (quadratic) | 400,000 | **$102.50 input + $10.00 output = $112.50** | 1,000 x 5.8 s = 5,800 s sequential |
| 1,000 calls of 10 rows, **shared 5k prompt only, no prior rows** | 5e6 tokens (linear) | 400,000 | **$2.50 + $10.00 = $12.50** | 5,800 s sequential; **about 116 s at 50-way parallelism** |
| 100 calls of 100 rows, shared prompt only | 5e5 tokens | 400,000 | **$0.25 + $10.00 = $10.25** | 100 x 50.8 s = 5,080 s sequential; about 102 s at 50-way |

**The finding that surprised me and that the project should not miss:** naive chunked emission where each chunk sees all previous chunks is **quadratic in input**, and the input bill can be **10x the output bill** ($102.50 vs $10.00). "Input is cheap" stops being true when you send it O(M^2) times. Any design here must answer "what does chunk i need to see of chunks 1..i-1?" — and the answer must be a bounded summary or constraint set, not the prior rows. This is the hardest engineering question in the bulk case and it has nothing to do with schemas.

Error exposure for case 2 is not close: 10 rows per call sits well inside the reliable regime, while the verbatim-transcription cliff (section 7b(B)) puts **0% perfect runs at 300 items**. And a failed chunk can be retried alone; a failed 400k-token generation cannot.

### Regime boundaries — where each approach dominates

Let **rho = k'/N** (fraction of the object that must be emitted) and **T** = number of turns over the same object.

| Axis | Boundary | Which wins |
|---|---|---|
| **Dollars** | Fragment emission wins for all rho < 1, but the *saving* is (1 - rho) x 98% (warm cache). At rho > 0.5 the saving is under half and probably does not repay the engineering. | Fragment for **rho below about 0.3**; a wash above that. Predicted Outputs **never** wins on dollars — it is at least as expensive as full regeneration, always. |
| **Wall clock** | Fragment beats speculation iff **rho < 1/S**. | S=3 gives fragment the win below **rho = 33%**. S=5 gives it below **20%**. S=1 (loaded server, MoE, unsupported model) means fragment always wins. |
| **Error probability** | Corruption grows with N ("each 1k-token increment progressively increases degradation" — DELEGATE-52) and compounds with T with no plateau to 100 turns. Fragment adds routing error and missed-related-update error, both roughly constant in N. | Full regeneration is acceptable at **small N and T=1**. Fragment wins increasingly as N and T grow. Crossover is likely in the low thousands of tokens; **nobody has measured it**. |
| **Feasibility** | N greater than max output tokens (64k-128k depending on model). | Above the cap, chunked emission is the **only** option. Not an optimisation — a requirement. |

**Summary of who wins where:**

| Regime | Winner | Margin |
|---|---|---|
| Small object (N under about 2k), single turn, any rho | **Full regeneration** | Fragment machinery is not worth it; JSON Whisperer's 31% is the realistic prize here and it costs a custom encoding |
| Medium object, rho above 0.3 | **Full regeneration, plus speculation if available** | Fragment saving is small; speculation is free to switch on |
| Medium or large object (N much greater than 2k), rho below 0.3, interactive | **Fragment emission** | 10-40x on dollars, 30-100x on latency; speculation is a distant second |
| Many turns over the same object (T at least 10) | **Fragment emission** | Correctness, not cost: full regeneration loses about 25% of content (frontier) and about 50% (all models) by turn 20 |
| N greater than max output tokens | **Chunked emission** | Full regeneration cannot run at all |
| Bulk generation of genuinely new content | **Chunked emission** | Only option; but watch the quadratic input trap |
| Self-hosted GPU, latency-only concern | **Speculative decoding** | You own the hardware, so latency *is* cost; n-gram lookup is free and needs no schema work |

### (A) A company exists to solve it — Morph Fast Apply

**Their own documented numbers vs their marketing numbers do not agree, and the docs are the conservative ones:**

| Claim | Docs (PRIMARY) | Marketing page (SECONDHAND, via search snippet) |

### (B) The measured savings converge on 30-40%, not on N/k — and here is the reconciliation

Two independent measurements of "emit a delta instead of the whole artifact":

| Source | Token saving | Latency saving | Artifact size |
|---|---|---|---|
| JSON Whisperer (EMNLP 2025 Industry) | **31%** | 1.46x-1.73x | small JSON, film-production objects |
| Morph Fast Apply (vendor docs) | **40%** | **1.8x** | 500-1000 line source files |

Landing in the same place from different domains is meaningful. **It also means my worked-example arithmetic of 39x is not what people actually measure**, and I should say why rather than wave it away.

The reconciliation is that these two measure a **different regime**. Both are editing artifacts of roughly 5,000-10,000 tokens where the edit touches a substantial slice — a refactor spanning several functions, a JSON edit that cascades into related fields. If rho = k'/N is around 0.3-0.5 in their workloads, then a 30-40% saving is *exactly* what the model in section 6 predicts. My 39x example assumed rho = 0.006 (120 tokens changing in a 20,000-token form), which is the "change the answer to Q3" case and is genuinely a different problem.

**So the honest statement is: the published savings for delta emission are 30-40% because the published experiments are all in the rho ~ 0.3-0.5 regime. Nobody has measured rho < 0.01 on a large object. The claimed 10-40x is arithmetic, not measurement.** Getting a real number here is the most valuable experiment this project could run, and it is cheap.

### (C) Budget-overrun incidents are a catalogued failure class

[SECONDHAND, from search snippets] "Token Budgets: An Empirical Catalog of 63 LLM-Agent Budget-Overrun Incidents, with an Affine-Typed Rust Mitigation as a Case Study", arXiv:2606.04056 — reportedly 63 confirmed production incidents across 21 sub-projects and 18 ecosystems, 2023-2026. Also circulating: a postmortem of an agent that burned $4,200 in 63 hours. **Neither is specifically about structured-output regeneration**, so this is background evidence that LLM cost blowups are real and operationally recognised, not evidence about our failure mode. Do not overclaim it.

### (D) A finding that CUTS AGAINST our input/output asymmetry argument — read this carefully

[SECONDHAND, from a search snippet of production cost-attribution writeups] *"Input tokens, not output tokens, dominate the overall cost in agentic coding, even when token caching is enabled, with cache-read input the largest single category by a wide margin."* And: *"Loops consume context quadratically in a way single calls do not, because step five carries everything steps one through four produced."*

This is true and it is not a contradiction, but it must be stated precisely or the project will make a false claim:

- **Per token**, output costs 50-200x a cached input token. That is verified (section 4+5) and is not in dispute.
- **Per workload**, whichever side dominates depends on the token *ratio*, not the price ratio. An agent loop that sends 100x more input tokens than it emits output tokens will be input-dominated despite the 50x price gap.
- **For the specific workload this project is about** — regenerate an N-token object, having sent that same N-token object as input — the ratio is 1:1, so the 50x price gap decides it and **output dominates by roughly 50:1**. The claim holds *for our case*.

**Recommended wording for the final writeup:** not "input is cheap and output is expensive" (too broad, and refutable by the agentic-coding data), but **"in a regenerate-the-whole-object turn the input and output token counts are equal, so the 50x price gap falls entirely on the output side."** That version is defensible.

## 8. The limit of my own argument: which case speculation helps, and which it cannot touch

Speculative methods need a draft that resembles the output. That single sentence draws the boundary, and the two motivating cases fall on opposite sides of it.

### Case 1, the form edit — speculation genuinely helps

The previous version of the form *is* a near-perfect draft. Acceptance rate alpha is close to 1 for every token outside the edited region. Predicted Outputs was built for precisely this. Prompt-lookup n-gram speculation finds the old document in the prompt with no API parameter at all. Expected gain 2x-6.5x latency. **Concede this fully: for latency alone on a form edit, existing machinery does most of the job with none of the engineering.**

What it still does not do, even here:
- It does not reduce the bill by a single token, and on OpenAI it raises it.
- It does not reduce the error rate by a single token, because it is provably distribution-preserving.
- It is unavailable on Anthropic and Google, unavailable with function-calling on OpenAI, and unverified with `response_format: json_schema`.

### Case 2, generating 10,000 new rows — speculation helps almost not at all

There is no draft. The rows resemble nothing in the prompt. Predicted Outputs has nothing to predict; n-gram lookup has nothing to look up.

**The honest exception, and it is not nothing.** A table of 10,000 rows against one schema repeats its *scaffolding* endlessly: the braces, the commas, and above all the JSON keys. Those tokens are highly predictable and two existing mechanisms already exploit them:

- **N-gram / prompt-lookup speculation** will match the repeated key sequences from earlier rows in the generated context and draft them for free.
- **Jump-forward decoding with a compressed FSM** (SGLang; the same idea in XGrammar) skips the LLM entirely wherever the grammar admits only one continuation, tokenizing the deterministic span and appending it directly. [PRIMARY-ish: https://www.lmsys.org/blog/2024-02-05-compressed-fsm/] Reported: **up to 1.6x throughput improvement on JSON decoding benchmarks**, and the blog explicitly names "long fixed prefixes like JSON keys" as where the win comes from.

So the scaffolding is close to free already — **on self-hosted inference**. Two things stop this from rescuing the bulk case:

1. **On a hosted per-token API you are still billed for every one of those tokens as an output token.** Jump-forward decoding is a server-side efficiency; it is not a discount. Nothing in OpenAI's, Anthropic's or Google's billing documentation gives a reduced rate for grammar-determined tokens.
2. **The row *values* are the point, and they get zero acceleration.** Whatever fraction of the output is genuinely new information is generated at the normal one-token-at-a-time rate, and that fraction is the part you are paying for.

### The ceiling that no decoding technique touches

400,000 output tokens exceeds every provider's per-response cap (128,000 on Claude Opus 5 / Fable 5 / GPT-5.4; 65,536 on Gemini 3.1 Pro; 64,000 on Haiku 4.5). **Speculative decoding does not raise max_tokens. It makes you hit the wall sooner.** For case 2, chunked emission is not an optimisation that must justify itself against alternatives — it is the only thing that runs. The machinery has to exist. The only design question is whether it is ad hoc or principled.

## THE STRONGEST CASE THAT THIS PROBLEM DOES NOT NEED SOLVING

*(My judgement, argued as hard as the evidence honestly permits.)*

**1. The latency complaint is already answered, by machinery that is free, standard, and provably safe.** Speculative decoding is in every serious inference stack — vLLM, SGLang, TGI, llama.cpp, and every major hosted provider's backend. It is distribution-preserving by construction (Leviathan Thm 3.8; vLLM ships a test asserting greedy-with-speculation equals greedy-without). Turning it on costs nothing and risks nothing. Where the old document is available, OpenAI, Cerebras, Fireworks and Mistral all expose a `prediction` parameter built for exactly the "regenerate a document with small changes" case, and OpenAI claims 3-5x for it. Prompt-lookup decoding gets ~2.4x with no parameter at all, just by putting the old document in the prompt. This is a solved engineering problem with a clean theory and a decade of momentum behind it.

**2. The measured payoff of the delta approach is 31-40%, and two independent teams agree.** JSON Whisperer (EMNLP 2025 Industry, Lightricks) measured **31% token reduction and 1.46x-1.73x latency** for LLM-emitted RFC 6902 patches. Morph, a company whose entire product is this, documents **40% fewer tokens and 1.8x faster**. Those numbers are *worse than what speculative decoding gives you for free*. If a technique costs a custom encoding scheme, a routing layer and a splice layer, and returns less than switching on a feature flag, it is hard to justify.

**3. The delta approach measurably *degrades* quality, and adds error modes that full regeneration does not have.** JSON Whisperer's edit quality came in **within 5% of full regeneration — i.e. slightly worse.** Plain RFC 6902 did not work at all: the authors had to invent EASE because "LLMs struggle with array index arithmetic" and "frequently miscalculate these shifts or conflate zero-based and one-based indexing." They further report that models editing via fragmented patches **"miss necessary updates"** — a field changes and its dependent field does not, because the model never saw it. Full regeneration cannot make that mistake. Aider's own docs note that the whole-file format "is the easiest for an LLM to use" and that diff formats introduce a failure class of their own (Gemini 2.5 Flash "frequently hits the maximum allowed reflections without successfully applying the code diff"). You are trading a known, gradual failure mode for an unknown, discrete one.

**4. Resending the document costs almost nothing, so the intuition that full regeneration is "wasteful" is half wrong.** With a warm prefix cache, resending N tokens as input costs **1.96%** of what regenerating them costs on GPT-5.6 Sol and Claude Opus 5, and **0.50%** on Claude Fable 5.1. Caching is automatic and on by default at OpenAI. The wasteful-looking part of the loop is already nearly free.

**5. The cheap levers are much bigger than the clever one, and each is one line of code.** Batch APIs cut every rate by 50% at OpenAI, Anthropic and Google. Model choice is a 17x lever on output price (GPT-5.6 Sol $20/MTok vs GPT-5.6 Luna $1.20/MTok). Effort/reasoning settings are another. A 10,000-row table job that moves from Sol to Luna and into the batch queue costs **1/34th** as much, with no new abstraction, no new failure modes, and no research. Against that, 31-40% is noise.

**6. Nothing here needs a framework anyway.** "Work out which part is needed, generate only that part, constrain it against that part's own schema" is a description of ten lines of application code: pick the sub-model, call the API with `response_format` set to that sub-model's schema, assign the result into the parent object. Pydantic already gives you the sub-model for free — `MyForm.model_fields['q3'].annotation` is the schema you need. Any team that wants this can have it this afternoon. A general library would be sugar over something that is not hard.

**7. And the evidence for the pain is thinner than the framing suggests.** I searched specifically for reports of repeated structured-output regeneration as a production bottleneck. I found a company selling a fix for the *code* case, one industry paper on the *JSON edit* case, and a catalogue of agent budget overruns that is not about this at all. There is no incident report, no vendor advisory, no widely-cited paper saying "schema-constrained regeneration is eating our budget."

## WHERE THAT CASE FAILS

*(My judgement. Point by point against the above. On balance I think the case above loses, and I say why at the end.)*

**1. Every speculative technique is latency-only on a hosted API. The money argument survives intact.** This is verified from billing documentation, not inferred:
- OpenAI: *"Any rejected tokens are still billed like other completion tokens generated by the API, so Predicted Outputs can introduce higher costs for your requests."* Best case you pay exactly the full-regeneration price; worst case more. There is no discount branch.
- Cerebras: rejected prediction tokens "billed at the output token rate" on Free Trial and Developer accounts.
- Microsoft: *"any rejected_prediction_tokens have the same cost implication as additional output tokens."*
- And the cleanest proof that latency and cost are separate goods: **Anthropic sells fast mode as "up to 2.5x higher output tokens per second" at $10/$50 per MTok against Opus 5's standard $5/$25 — 2.5x the speed for 2x the price.**

So point 1 of the case above kills only the *speed* argument for deltas. The dollars argument is untouched, and on current prices an output token costs **50x** a cached input token (GPT-5.6 Sol, Opus 5, Sonnet 5, Haiku 4.5), **60-80x** (GPT-5.5, GPT-5, Terra, Luna), or **200x** (Claude Fable 5.1). Emitting k tokens instead of N is the only lever that touches that.

**2. The 31-40% figure is from the wrong regime, and the case above leans on it far too hard.** Both measurements edit ~5,000-10,000-token artifacts where the change touches a substantial slice — rho = k'/N is plausibly 0.3-0.5. At that rho the model in section 6 *predicts* a 30-40% saving; the measurements confirm the model rather than bounding it. The user's motivating case is a **120-token fragment of a 20,000-token form: rho = 0.006**, where the same model predicts **39x on dollars and 109x on latency**. **Nobody has measured that regime.** Citing 31% as the ceiling is an extrapolation across two orders of magnitude in rho, and it is the weakest link in my own brief.

**3. Speculation is provably distribution-preserving, which is exactly why it cannot fix the failure that matters.** This is the decisive point and it is not close. The evidence that models silently corrupt what they were told to copy is now measured, from two independent groups:
- **DELEGATE-52** (Laban, Schnabel, Neville; arXiv:2604.15597, 2026-04-17): 19 models across 52 professional domains. Frontier models — Gemini 3.1 Pro, Claude Opus 4.6, GPT-5.4 — **corrupt an average of 25% of document content by the end of long workflows.** Mean reconstruction across all models falls to ~50% after 20 interactions. *"Each 1k-token increment progressively increases degradation."* *"Degradation accelerates with horizon length; no plateau is observed up to 100 interactions."*
- **Verbatim transcription stress test** (arXiv:2601.03640, 2026-01-07): copying N constants verbatim gives 44-45% perfect runs at N=100, **0% perfect runs at N=300** (15.65% mean match), **0% at N=500** (7.12%). Open-weights models only — but the shape matches DELEGATE-52's frontier result.

Speculative decoding reproduces every one of those errors *exactly*, by design, and bills you for the rejected tokens on the way. **The only technique that reduces the number of tokens the model re-decides is not re-decoding them.** That is what fragment emission is.

**4. Speculation needs a draft resembling the output, so it does nothing for bulk generation.** For 10,000 genuinely new rows there is no draft. N-gram lookup and jump-forward decoding will accelerate the repeated JSON scaffolding (up to 1.6x on JSON benchmarks) but not the values, and on a hosted API even the scaffolding is billed at full output rate. Case 2 gets essentially zero benefit from every technique in my brief.

**5. No decoding technique raises the output ceiling, and case 2 is over it by 3-6x.** 400,000 output tokens against a 128,000-token cap. Chunked emission is compulsory, not optional. Whatever the verdict on case 1, the machinery for case 2 must be built; the only question is whether it is designed or improvised.

**6. Predicted Outputs is a narrow and apparently unmaintained feature.** As of 2026-09-07 the supported-model list on both OpenAI's and Azure's pages is still gpt-4o / gpt-4o-mini / gpt-4.1 family — **no GPT-5-family model, roughly 1.5 years after launch**. It excludes `tools`, so any structured output emitted via function calling cannot use it at all, and function calling is how a large share of production structured output is produced. It has no documented compatibility statement with `response_format: json_schema`. There is no Anthropic equivalent and no Google equivalent. Microsoft's own doc warns it can *increase* latency when rejections exceed acceptances. It is not the broad safety net point 1 makes it out to be.

**7. Speculation plus schema-constrained decoding is unmeasured, and there is reason to think they fight.** Grammar validation is the non-parallelisable step in constrained decoding (up to 37.5% higher latency at batch 512), and every speculated token must be validated against the grammar. vLLM's own notes place spec-decoding/jump-forward integration in ongoing work. **NEGATIVE RESULT: no published measurement of speculative decoding running with a JSON schema grammar on a large structured output.** The "3-5x" number quoted in the case above has never been demonstrated for our workload.

**8. Batch and model-downgrade are real levers but they are orthogonal, not competing.** You can apply both to fragment emission too and multiply the savings. "Use a cheaper model" is not an argument against reducing token count; it is an argument for doing both.

**9. And the framework argument cuts the other way.** Point 6 above says it is ten lines of code. It is ten lines *once you have decided which sub-schema to target and how to splice the result back*. Those two steps are the whole problem: routing (which part of the schema does "change the answer to Q3" mean?) and safe assembly (does the spliced object still satisfy the parent schema and its cross-field invariants?). JSON Whisperer's two documented failure modes — array index arithmetic and missed related updates — are exactly those two steps failing. That is a real design problem, not sugar.

## VERDICT

**(c) genuinely open — but narrower and better-shaped than the original framing, and the strongest ground is not the one the user led with.**

| Sub-claim | Verdict |
|---|---|
| Full regeneration is too **slow** for the edit case | **Mostly answered** by speculative decoding where it is available (2-6.5x, free, safe). The residual gain from fragments is real but only in the small-rho regime, which nobody has measured. Weakest ground for the project. |
| Full regeneration costs too much **money** | **Open, and the arithmetic is strong.** No speculative method reduces billed output tokens; OpenAI's raises them. Output costs 50-200x cached input. This survives every counterargument I could build. |
| Full regeneration **corrupts** untouched regions | **Open, and this is the strongest ground by a distance.** DELEGATE-52 measures 25% content corruption on frontier models, degrading with document size and with turn count and not plateauing to 100 turns. Speculative decoding is provably incapable of helping, because it is provably distribution-preserving. |
| Full regeneration hits **hard ceilings** | **Not open — settled against full regeneration.** 400k > 128k. Chunking is compulsory. |

**The one experiment that would settle it, and it is cheap:** take a real Pydantic model of 10,000-20,000 tokens, change one leaf value, regenerate the whole object, and diff every field that was supposed to be untouched. Do it across turns. Report the corruption rate, the dollars and the latency for (i) full regeneration, (ii) full regeneration with `prediction`, (iii) fragment emission. **That experiment appears not to have been run for schema-constrained output** — DELEGATE-52 is prose documents, the verbatim work is code, and JSON Whisperer measured a different regime on small objects. An absence this specific, in a question this practical, is itself the finding.
